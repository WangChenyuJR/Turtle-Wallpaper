## ① 荷叶 / 荷花 —— 改成真正的侧视立绘

**代码位置**：`src/plants.js` → `Plant._drawSurfacePlant()`（第 430~543 行）

**现状拆解**（为什么看起来还是俯视）：
1. 整片叶子靠 `ctx.scale(1, CONFIG.plants.surfaceSquash)`（现 0.58）压扁 → 只是"俯视的圆压成椭圆"，识别度仍是俯视。
2. **叶脉从叶心 360° 放射**（`for i < S.veins`，7~12 条）→ 这是最典型的俯视特征。
3. **花是 360° 放射花瓣**（双层，6~13 片绕一圈）→ 侧视里看到"俯视的花"，假得最明显。
4. 茎只画到 `r * 0.95`（16~30px 长），悬在水面下一点点就断了，**没有根插到池底**。
5. 花心是"不规则小团 + 花蕊点"，也是俯视画法。

**建议方案**（推荐全做）：

| 项 | 现状 | 建议 |
|---|---|---|
| 压扁比 | `surfaceSquash: 0.58` | **0.20 ~ 0.28**（叶面几乎平铺在水线上） |
| 叶片轮廓 | 椭圆 + 波浪边 + V 口 | 保留（已经做得不错），但**边缘改成微微上翘**——侧视荷叶最标志性的特征 |
| 叶脉 | 360° 放射 7~12 条 | 改为 **3~5 条沿水平方向的中脉**，从叶心向左右延伸 |
| 根茎 | 到 `r*0.95` 就断 | 从叶心 **画到 `world.groundYAt(x)`**（池底），两段 quadratic 带水流摆动，线宽 2.5~3.5px，越深越暗（alpha 渐变） |
| 花 | 360° 放射花瓣 | **侧视花冠**：花梗从水面竖直升起（睡莲矮 ≈0.5r，荷花高 ≈0.9~1.2r），花瓣左右对称张开、花心朝上 |
| 浮动 | `bob = sin(t)*1.4` | 与阶段 8-④ 的 1D 水面波联动，水一荡荷叶跟着起伏（顺手的加分项） |

**不动的部分**：`_buildShape()` 的逐株随机外形 + `seed` 存档复现、`shelter` 遮蔽查询、生物推开水面的物理 —— 全部保留。

**可选风格分叉（需要你选）**：
- **A 写实向**：叶面压到 0.20、根茎清晰可见、花直立。最像真实池塘，但荷叶"存在感"变弱（画面上的绿块变小）。
- **B 萌系向**：叶面压到 0.30，保留明显弧度的"半月形"叶片 + 一条粗根，花矮而胖。辨识度高、可爱，但离真实略远。
- **C 折中（推荐）**：叶面 0.26，叶片上翘明显，根茎 2.5px 半透明；睡莲矮花、荷花高花分开处理。

## ② 地形：晒台/岸 太高太陡

**代码位置**：`src/config.js` → `CONFIG.layout`；`src/world.js` → `resize()` 里的 `_bankPts`（第 103~109 行）

**实测数据（1920×1080）**：

| 量 | 当前值 | 换算 |
|---|---|---|
| `waterY` | 0.34H | 367px（水线） |
| `bankTopY` | 0.15H | **162px（岸顶高出水线 205px）** |
| `platform.topY` | 0.235H | 254px（中央晒台高出水线 113px） |
| `bankSpan` | 0.24W | 461px |
| 登岸段坡度 | `_bankPts` t∈[0.2,0.4] | **92px 水平爬升 184px ≈ 63°** ← 问题核心 |

龟的登岸流程是：游到 `shorePointNear()`（岸线外侧）→ 在陆列上沿 `groundYAt` 爬上目标点。也就是说**它一上岸就要面对 63° 的陡坡**，所以看起来"上不去 / 不自然"。

**建议方案**：
1. `bankTopY` 0.15 → **0.26**（岸顶只高出水线约 0.08H ≈ 86px）
2. `shoreRatio` 0.4 → **0.5**（岸线更靠内，岸上坡有更多水平空间）
3. `_bankPts` 岸上段从"两段折线"改为 **"边缘小平台 + 一条长缓坡"**，登岸坡度压到 **20~25°**
4. **左右岸各加一块低矮晒背台**（新增 `CONFIG.layout.baskingLedges`），台面只比水线高 5~8%（约 10~20px）—— 龟一上岸就有落脚点，不用先爬坡
5. 水下入水坡放缓（`wY + (bY-wY)*0.62` → `0.75`），减少"水下迎面一堵墙"的突兀感（与 ③ 联动）
6. 中央晒台 `topY` 一并降低到 0.28 左右

**⚠ 需要你拍板的歧义点**：你说的是"**左右两侧的**晒台"。但现在的晒台（`platform`）是**池子中央那个岛**，左右两侧是岸。两种理解对应两种做法：

- **方案甲**：把左右两侧的岸降低，做成左右两块"矮晒背台"（岸边一大片缓坡干地），中央岛保留或去掉。
- **方案乙**：保留中央岛（也降矮），另外在左右岸边线处各加一块**小的贴水矮台**（像真实的晒背石/木台），岸本身高度也一起降。
- **方案丙（我推荐）**：乙 + 岸顶降到 0.26。既有左右就近的落脚点（龟不用横穿水面），也保留中央岛的构图趣味。

## ③ 水下墙体碰撞：硬钳制 → 沿墙滑行

**代码位置**：`src/world.js` → `constrainToWater()`（第 285~322 行）；`src/fish.js` 第 243~248 行；`src/turtle.js` 第 419~444 行

**现状问题**：
1. `constrainToWater` 是**硬钳制**：算出合法点后**直接把生物拽回去**（`this.x = c.x; this.y = c.y`），没有物理过渡。
2. 钳制是**轴对齐**的：x 钳到水域左右边界、y 钳到 `groundYAt - margin`。沿斜岸时 → 表现就是**贴着墙往下滑**，或者被瞬移到坡面上半截。
3. `fish.js` 撞墙后 `vx *= -0.5 / vy *= -0.5` → 速度**整体反向**，鱼会"撞墙掉头"，视觉上像"撞一下就往下掉"。
4. 角落（池底∩岸坡、晒台两侧根部）两个约束互相打架 → 抖动 / 卡住。
5. 深层原因：乌龟的 `depth` 与 `y` 双向同步（`_syncYFromDepth` / `_syncDepthFromY`），一旦 y 被外部钳制，depth 会被重新解释成别的深度 → 造成"下滑"的观感。

**建议方案**：
1. `world` 新增 `wallInfo(x, y, margin)`：返回最近障碍面（水线 / 池底 / 左右水下岸坡 / 晒台侧壁）的**法线 n** 与**穿透深度 d**。
   - 岸坡法线由 `groundYAt(x)` 的导数求得；晒台侧壁按竖直墙处理。
2. 生物移动改成**软约束（Boids 式墙避让）**：
   - 离墙 18px 内施加**沿法线的加速度**，越近越强；**切向速度全部保留** → 自然沿墙滑行。
3. **硬兜底保留**，但速度改成正经反射：`v = v_t + (-e)·v_n`，**e ≈ 0.25~0.4**（保留 60~75% 切向速度），绝不整体反向或清零。
4. **脱困机制**：切向速度接近 0（真卡在角落）时，给一个沿墙方向的随机助推 + 短暂冷却，避免死循环。
5. **状态白名单**：只有 `SWIM` / `SEEK_FOOD` 启用墙滑；`CLIMB_OUT` / `BASK` / `RETURN` 是**故意穿越水陆边界**的状态机，必须跳过（否则龟上不了岸）。这一点是历史踩过的坑，不能省。
6. `depth` 同步要区分"主动下潜"与"被钳制修正"：钳制后不立刻反推 `depthGoal`，避免生物自己"追着"墙面深度走。

**验收（新增 `_diag_wall.mjs`）**：
- ① 朝墙直冲 30s **不穿透**（每帧 `isWater` 为真）
- ② 撞击后切向速度 ≥ 撞击前的 **60%**
- ③ 运动方向与墙面夹角 **< 35°**（"沿墙走"而不是"往下滑"）
- ④ 角落 60s 内位置熵 > 阈值（**没卡死**）

## ④ 水面动画：环状扩散 → 拖拽尾迹（本次最大改造）

**代码位置**：`src/waterwave.js`（全屏 2D 波动方程）、`src/world.js` → `_drawWaveSurface()` / `_drawRipples()` / `addWake()`、`src/main.js` → `_cursorWake()` + 生物起波段（第 850~897 行）

**现状问题（"环状往外延伸"的三个来源）**：
1. **主源**：`waterwave.js` 是**全屏 2D 网格**波动方程（`CELL=7`，1920×1080 ≈ **42k 格/帧**）。2D 波从扰动点出发必然**向四面八方扩散成环** —— 这是数学性质，调参救不了。
2. **直接元凶**：`world._drawRipples()` 画的**同心椭圆环**（`ellipse(rp.r, rp.r*0.4)`），入水/产蛋/龟露头时触发，肉眼看到的就是"一圈圈往外扩"。
3. **不该出现的环**：`main.js` 第 869~882 行对**水里所有鱼**无条件扰动，**不管多深** —— 池底游的鱼也会在水面画出一圈环。

**建议方案（推荐 B 档）**：

**A 档（轻量·缓解）**：保留 2D 波场，只做三件事 —— 删掉 `_drawRipples` 同心环、生物扰动加**深度权重**（越深越弱，深水几乎为 0）、加一层"拖尾条带"视觉盖在上面。
- 优点：改动小、风险低、一天能完成。
- 缺点：2D 波本身**仍然是环状扩散**，只是被拖尾盖住一部分；CPU 开销不变。

**B 档（彻底·推荐）**：把波场 **2D → 1D 水面高度场**。
- `h[i]` 沿屏幕 x 分布（步长 4px → 1920 宽仅 **480 格**），一维波动方程：
  `hn[i] = 2h[i] - hp[i] + r(h[i-1] - 2h[i] + h[i+1])`
- 波**沿水平方向传播** → 天然就是"涟漪沿着水面跑"，**物理上不可能出现环状扩散**。
- 水线本身按 `h(x)` 真实上下起伏（`surfaceAt(x) + h·k`），侧视剖面的正道。
- **性能：42k 格/帧 → 480 格/帧，降约两个数量级。** 你一直很在意 CPU 占用，这是白赚的收益。
- 代价：`_drawWaveSurface()` 的竖直梯度着色要重写（水下光斑改由已有的 `fx.drawCaustics` 承担）；`_diag_render.mjs` 的假 `ctx.createImageData` 桩要同步调整。

**两层都在 B 档里做**：
1. **拖尾层 `wakeTrails`**：每条 `{x0, x1, life, strength}`，沿水线画一条细亮痕 + 尾部泡沫点；
   - 痕迹**留在生物身后**（上一帧位置 → 当前帧位置），不是以生物为中心 → 这就是"拖拽感"；
   - 随时间**被拉长变淡**，而不是向外扩散；
   - 强度按**离水面深度**衰减（浅水强、深水几乎无）。
2. **鼠标交互分层**：
   - 鼠标在**水面附近**（`|y - surfaceAt(x)| < 30`）→ 水面被"拖"出一条尾迹；
   - 鼠标在**深水区** → 改为**水下搅动**（气泡上涌 + 泥沙翻起 + 弱上升流），**不再扰动水面**。
   - 理由：侧视剖面里"水面"只是画面上的一条线，一个在水下的光标不该在水面起波。
3. **入水溅射**改形：垂直水花 + 短横痕，不再画椭圆同心环。
4. **接口保留**：`wave.disturb / disturbLine / energy / calm` 名字不变（内部实现换掉），`main.js` 与诊断脚本改动量最小。

**验收（新增 `_diag_wave.mjs`）**：
- ① 扰动后能量衰减到 0（回归）
- ② 波峰**沿 x 传播**（跨帧追踪，位置单调移动）
- ③ 能量**不在 y 方向扩散**（1D 场天然满足，作为回归守卫）
- ④ 拖尾轨迹数量上限 + 淡出曲线正常
